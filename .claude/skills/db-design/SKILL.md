# DB design

Input: approved `system-design.md`. Output: `specs/<feature>/db-design.md` (template below), then migration SQL during build.
The document is the thing a reviewer approves, so it must show the schema itself: a prose summary of a table is a failure. If no table or column changes, say so in one line and still list the query paths the feature adds and the index (existing or new) that serves each.

## Read first
`docs/database-schema.md` (ER diagram and table list), the newest files in `api/migrations/` (goose, embedded, applied on API start; next number follows the highest), the repos in `api/internal/infrastructure/postgres/` (the real queries), `docs/seed-data.md`. Postgres ids equal OpenFGA object ids (real UUIDs). Copy the style of a nearby migration (`00006_blueprints.sql`, `00009_estimate_sessions.sql`, `00011_session_per_blueprint.sql`) rather than inventing one.

## Method (in this order)
1. **List the access paths first.** From the system design, write every query the feature will run: who calls it, the filter columns, the sort, the expected row count, read or write, and how hot it is. Tables and indexes come from this list, never the other way round.
2. **Model the data.** Entities, owner (which domain), cardinality (1:1, 1:N, N:M), lifecycle (immutable, append-only, mutable, cache), who deletes it.
3. **Write the DDL** for every new or changed table in full (see schema rules).
4. **Choose indexes** from the access paths (see indexing rules); say which path each one serves, and which tables need none.
5. **Plan the rollout** (expand -> backfill -> contract) and the rollback.
6. **Prove it**: dry run and EXPLAIN (see verification).

## Schema rules (this repo's conventions)
- **Keys**: ids are `uuid` generated by the API (`idgen`), no serials, no `gen_random_uuid()` for domain rows (the id must equal the OpenFGA object id). A 1:1 child is keyed by the parent id (no surrogate id), as `estimate_sessions`. A child ordered under its parent uses a composite key `(parent_id, seq|version)`, as `blueprint_versions` and `estimate_messages`. Do not add a surrogate id nobody references.
- **Tenant scoping**: a tenant-owned top-level table has `tenant_id uuid NOT NULL REFERENCES tenants (id) ON DELETE CASCADE`; a child of a tenant-scoped parent may skip it only if every query loads the parent under `WHERE tenant_id = $1 AND id = $2` first (state this, with the precedent). A project-scoped table uses the composite FK `(project_id, tenant_id) REFERENCES projects (id, tenant_id)`, so a row can never point at another tenant's project.
- **Types**: `uuid`, `text`, `integer`/`bigint`, `boolean`, `timestamptz` (never `timestamp`), `numeric` for money (never float). No `varchar(n)`: bound with `CHECK (char_length(x) <= n)` only if the rule is real.
- **Constraints do the validation the app would otherwise forget**: `NOT NULL` by default; `CHECK` for ranges and closed value sets (`kind text NOT NULL CHECK (kind IN (...))`); `UNIQUE` for every natural key; `FOREIGN KEY` for every reference, with `ON DELETE` chosen on purpose (CASCADE for owned children, RESTRICT/none for references like `created_by`, SET NULL only when the row must survive and the column is nullable). A new FK or UNIQUE on a table with data must not be violated by existing rows.
- **JSONB only for opaque engine state or a payload the SQL never filters or joins on** (plan `model`, `checks`). If you filter, sort or join on a field, it is a column. Do not store arrays of ids in jsonb: use a child table.
- **Normalize to the point of no duplicated facts** (3NF). Denormalize only a measured read problem, and then name the column that is derived, how it stays right, and who writes it. No status column that restates something already stored (see 00011 comment).
- **Immutable rows are append-only**: no `updated_at` on a table nothing updates; mutable rows carry `updated_at timestamptz NOT NULL DEFAULT now()`. Every row has `created_at timestamptz NOT NULL DEFAULT now()` and, if a person made it, `created_by uuid NOT NULL REFERENCES users (id)`.
- **No generic tables** (`attributes`, `kind`-discriminated shared tables, EAV). Each domain owns its tables, with literal table names in its repo.
- **Postgres is the display record**: no role/affiliation/permission columns that code branches on; authorization lives in OpenFGA.
- **Names**: plural snake_case tables, `<table>_<cols>_idx`, `<table>_<cols>_key` (unique), `<table>_<cols>_check`, FK columns `<singular>_id`.

## Indexing rules
- Every query path in the access list is served by the PK, a UNIQUE, or a named index. Write the mapping in the doc: `query -> index -> why it is enough`. A path with none must say why a scan is fine (tiny table, bounded by the parent).
- Collection queries here are `WHERE tenant_id = $1 AND id = ANY($2)`, plus `project_id` and a sort. Composite index order: equality columns first, then the range/sort column; the leading column must be the one every query filters on (`tenant_id`).
- A composite PK already indexes its leading columns; do not add a second index on the same prefix. A FK column that is deleted-by (ON DELETE CASCADE) or joined on needs an index whose leading column is that FK (Postgres does not create one), unless the PK already leads with it.
- Partial index (`WHERE deleted_at IS NULL`, `WHERE ok`) when the query always has that predicate; covering (`INCLUDE`) only for a proven hot read. GIN on jsonb only if a query uses `@>`/`?`; none exists today.
- Each index costs every write and storage: justify it by a query, and do not add speculative ones. For a table that is small and read by parent id, "PK only" is a correct answer.
- Create on a large table `CONCURRENTLY` (`-- +goose NO TRANSACTION`, one statement per migration file section).

## Query optimization rules (design-time)
- No N+1: a list needs one query (or one `= ANY($n)`), not one per row; write the batch query in the access list.
- Select named columns, never `SELECT *`; list endpoints must not load large jsonb (`model`, `brief`) when the view does not show it (see `ListVersions` "without brief or model").
- Pagination is a non-goal here; bound every list by its parent (project, blueprint) instead, and say the expected maximum.
- Writes that must be atomic are one transaction (`Create` inserts blueprint, version 1 and owner grant together); concurrent appends are guarded by the PK or `base_version` (409), not by a read-then-write.
- Idempotent writes use `INSERT ... ON CONFLICT DO NOTHING/UPDATE` on a named key.
- Check the plan with `EXPLAIN (ANALYZE, BUFFERS)` on the seeded data for every new query path that is not a PK lookup (record the node type: Index Scan, not Seq Scan, or why Seq Scan is fine).

## Never break the running system
Old and new code both run against the schema during a rollout. Forbidden in one step: drop/rename a column or table in use, change enum/CHECK value sets, NOT NULL -> NULL, new NOT NULL column without DEFAULT, narrowing a type, adding a UNIQUE/FK that existing rows violate.
- **Expand -> backfill -> contract.** Release N: add nullable or defaulted columns/tables/indexes (new code writes both shapes). Between: backfill in batches (`WHERE id IN (SELECT ... LIMIT 1000)` in a loop, never one `UPDATE` of a big table, never inside the schema transaction). Release N+1 or later: add the constraint (`ADD CONSTRAINT ... NOT VALID`, then `VALIDATE CONSTRAINT` separately; `SET NOT NULL` only after a validated CHECK) and drop the old shape once no code reads it.
- Lock awareness: say which statements take `ACCESS EXCLUSIVE` (most `ALTER TABLE`) and why they are quick (no rewrite; since PG 11 `ADD COLUMN ... DEFAULT <constant>` does not rewrite). Set `lock_timeout` for DDL on a hot table.
- A rollback of the app must still work on the new schema (the old build ignores new things), and the Down migration must work or say why it is irreversible (data loss is stated, not hidden).
- Mark an unavoidable exception `-- force-allow-breaking: <reason>` and justify it in the doc; `scripts/check-migrations.sh` rejects the rest (it reads whole statements: also constraints without `NOT VALID`, `CREATE INDEX` without `CONCURRENTLY`, type changes, dropped defaults/constraints/indexes, bulk DELETE/UPDATE/TRUNCATE; new tables of the same migration are exempt). The flag applies to the one statement it sits on or precedes, and its reason is required.
- Never edit a committed migration; add a new one (a hook blocks it). One concern per migration file; the number follows the highest.
- Seed and docs in the same change: new tables to `Truncate` (`postgres/db.go`, FK order; `make seed` fails otherwise) and `internal/seed/world.go` if demo data is needed; update `docs/database-schema.md` (diagram and table) and `docs/seed-data.md`.

## Verification (evidence, not claims)
- Dry run Up and Down inside a rolled-back transaction on the live schema (`BEGIN; \i migration; ROLLBACK;`) and on a copy with the seed loaded; paste the result.
- `make check` (runs `scripts/check-migrations.sh`), then start the previous build against the migrated database and smoke-test it.
- `pg_dump` restore point before applying anywhere that is not a demo database.

## Output template (`specs/<feature>/db-design.md`)
Every heading below is required; write "none" with a reason rather than dropping one.

1. **Summary**: what data the feature stores and why, in 3 lines. Next migration number.
1b. **Current schema touched**: the existing tables, columns and migrations (by number) this feature reads, alters or references, and the precedent it follows.
2. **Access paths**: table `# | query (what, by whom) | filter / sort | rows | frequency | read/write`.
3. **ER diagram**: a Mermaid `erDiagram` of the new and changed tables plus only the tables they relate to (parents and direct children), each entity listing its columns with type and PK/FK/UK. Mark new tables and columns (`%% NEW`). Not the whole database.
4. **Table schemas**: for each new or changed table, the full DDL as it will be in the migration (columns, types, NOT NULL, DEFAULT, PK, FK with ON DELETE, UNIQUE, CHECK), then a column table `column | type | null | default | meaning/source`. For an altered table show the exact `ALTER` statements and the resulting columns that changed.
   Follow each change with a **Backward compatible because** line: why the previous build keeps working against the new schema (nothing old reads or writes it, or it is defaulted/nullable).
5. **Design decisions**: why this key, why this tenant scoping, why these FK actions, why jsonb vs columns, what was not denormalized and why, what is deliberately not added (with the precedent in an existing migration).
6. **Indexes**: table `index | table (columns, order, partial?) | serves query # | type | unique? | cost note`, plus the tables that rely on the PK only and why that is enough. Index DDL included.
7. **Query plans**: the SQL of each non-PK query path and its `EXPLAIN` node (filled at build time, filled with the expected node at design time).
8. **Migration plan**: file names and the Up/Down SQL (or the key statements), the expand/backfill/contract steps with the release each lands in, lock/duration notes, rollback behavior with old and new code.
9. **Checks**: the checklist below, ticked, each tick with evidence or the reason.
10. **Docs and seed changes**: `docs/database-schema.md`, `docs/seed-data.md`, `Truncate`, `world.go`.
11. **`force-allow-breaking` exceptions**: none, or each one justified.

Checklist:
- [ ] No drop/rename of used columns or tables; no enum or CHECK change on existing tables; no new NOT NULL without DEFAULT
- [ ] Tenant scoping stated per table (column, composite FK, or parent-first with precedent)
- [ ] FK `ON DELETE` chosen on purpose; UNIQUE for each natural key; CHECK for each closed set or range
- [ ] Every access path maps to a PK, UNIQUE or named index; no redundant index; FK columns that cascade are indexed or PK-led
- [ ] No N+1, no `SELECT *`, large jsonb not loaded by list queries
- [ ] Down migration works (or irreversibility stated with the data lost)
- [ ] `Truncate`, seed, `docs/database-schema.md`, `docs/seed-data.md` updated
- [ ] Dry run in a rolled-back transaction; previous build smoke-tested; restore point noted

Run `design-reviewer`, then gate: the user approves. A db-design.md with no DDL, no ER diagram or no index/query mapping is not ready for review.
